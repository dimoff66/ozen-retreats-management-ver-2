# Ozen Retreats Management

Веб-приложение для управления ретритами, гостями, размещением по комнатам, картами домов, заселением, регистрацией и трансферами.

## Технологии

- Next.js
- React
- TypeScript
- Tailwind CSS
- Supabase
- PostgreSQL
- Supabase Storage

## Архитектура

Приложение построено по слоям:

```text
Component
   ↓
entityService
   ↓
database.ts
   ↓
Supabase
```

### Компоненты

React-компоненты отвечают за интерфейс и вызывают сервисы сущностей.

Компоненты не должны обращаться к Supabase напрямую.

### Сервисы

Сервисы содержат прикладную и бизнес-логику.

Основные сервисы:

```text
usersService
retreatsService
housesService
roomsService
retreatRoomsService
guestsService
guestStatusesService
houseMapsService
```

Сервисы работают только через объект `db`, экспортируемый из `database.ts`.

### database.ts

`src/services/database.ts` — единственный низкоуровневый адаптер базы данных.

Он экспортирует единый объект:

```ts
db.users
db.roles
db.houses
db.rooms
db.houseMaps
db.retreats
db.retreatRooms
db.guests
db.guestStatuses
db.taxiRides
db.taxiGuests
```

Типичные методы:

```ts
getAll()
getById()
getByRetreatId()
create()
update()
delete()
```

Все прямые запросы к Supabase должны находиться только в этом файле.

Такое разделение позволяет в будущем заменить базу данных без переписывания компонентов и прикладных сервисов.

# Отображение названия комнаты

Отображаемое название комнаты формируется в `roomsService`.

Если название дома заканчивается на строчную `s`, последняя `s` удаляется, а между названием и номером комнаты ставится пробел.

Пример:

```text
Buddhas + 3
→ Buddha 3
```

Во всех остальных случаях название дома и номер соединяются без пробела.

Пример:

```text
Osho + 4
→ Osho4
```

Если карта относится непосредственно к одному самостоятельному дому, на карте отображается только номер комнаты.

# Сортировка комнат

Комнаты сортируются по:

1. названию дома;
2. буквенной части номера;
3. числовой части номера.

Пример правильного порядка:

```text
A1
A2
A9
A10
B1
B2
```

Числовая часть сортируется как число, а не как строка.

# retreat_rooms

```text
id
retreat_id
room_id
max_guests
```

Глобальная доступность комнаты и доступность комнаты для конкретного ретрита — разные вещи.

Комната доступна для ретрита только если:

1. `rooms.is_available = true`;
2. существует запись в `retreat_rooms`.

Отсутствие записи в `retreat_rooms` означает, что комната для данного ретрита недоступна.

`max_guests` определяет максимальное количество гостей в комнате для данного ретрита.

Значение по умолчанию:

```text
1
```

## Настройка комнат ретрита

Комнаты группируются по домам.

Для каждого дома доступны массовые действия:

- сделать все комнаты доступными;
- сделать все комнаты недоступными;
- установить одинаковое `max_guests` для всех комнат.

Глобально недоступную комнату нельзя включить только на уровне ретрита.

# guest_statuses

```text
id
guest_id
status
room
updated_by
changed_at
```

История статусов не перезаписывается.

Каждое изменение создаёт новую запись.

Основные статусы:

```text
booked
arrived
checked_in
not_coming
```

Поле `room` хранит текстовое отображение комнаты на момент изменения статуса.

`updated_by` указывает пользователя, который выполнил действие.

`changed_at` хранит время изменения.

Текущий статус гостя определяется как его последняя запись.

В экране истории должно выглядеть как 
"10:22 Пользователь Елена назначил для Bryan Hump комнату HS2"
"10:37 Пользователь Улисес заселил Bryan Hamp в комнату HS2"

и т.д.

# Получение статусов

Статусы загружаются сразу для всего ретрита.

Используется метод:

```ts
guestStatusesService.getLatestForRetreat(retreatId)
```

Он возвращает:

```ts
Map<number, LatestGuestStatus>
```

где ключ — `guestId`.

Это позволяет не выполнять отдельный запрос к базе данных для каждого гостя.

# house_maps

Карта дома содержит:

```text
id
house_id
bg_image_url
room_positions
```

`room_positions` хранится в JSON.

Карта может быть назначена:

- самостоятельному дому;
- группе домов.

Карта содержит:

- фоновое изображение;
- позиции комнат.

Позиция комнаты хранится в процентах относительно размера изображения:

```json
{
  "room_id": 12,
  "x": 42.5,
  "y": 67.1
}
```

Координаты `x` и `y` находятся в диапазоне:

```text
0–100
```

Использование процентов позволяет сохранить расположение комнат при изменении размера экрана.

# 24. Требования к архитектуре кода

Работа с базой данных должна быть разделена на слои:

```text
UI Component
    ↓
Service
    ↓
Database Adapter
    ↓
Database
```

Компоненты интерфейса не должны выполнять прямые запросы к базе данных.

## Организация `src/`

```text
src/
├── app/                         # маршруты Next.js и глобальные стили
├── features/dashboard/          # экран и компоненты дашборда
│   ├── Dashboard.tsx            # серверная загрузка данных дашборда
│   ├── DashboardClient.tsx      # клиентское состояние и координация действий
│   ├── components/              # навигация, сводка, карта, каталог гостей
│   └── model.ts                 # UI-константы и типы навигации
├── services/                    # бизнес-правила, операции и подготовка данных
└── lib/database/                # адаптер данных
```

Страничные и повторно используемые компоненты находятся рядом с функциональностью,
к которой относятся. Серверный компонент feature загружает данные через сервис;
клиентские компоненты отвечают за интерактивность. Сервисы не импортируют компоненты
или UI-модели и не обращаются к базе в обход адаптера.

# 25. Database Adapter

Все низкоуровневые запросы к базе должны находиться в одном объекте.

Пример концепции:

```ts
db.users
db.houses
db.rooms
db.retreats
db.guests
db.guestStatuses
```

Каждая сущность имеет стабильный набор методов, например:

```ts
getAll()
getById()
getByRetreatId()
create()
update()
delete()
```

Прямое использование Supabase вне этого слоя не допускается.

Это необходимо для того, чтобы при смене базы данных остальной код приложения не требовал существенной переработки.

# 27. Загрузка данных компонентами

Списочный или рабочий компонент загружает необходимые ему данные самостоятельно.

Не следует загружать данные сущности в корневом компоненте только для того, чтобы передать их вниз через props.

# 28. Требования к JSX

В JSX не должно быть бизнес-расчётов.

Данные для отображения следует подготовить до `return`.

Допускаются простые условия:

```tsx
{isOpen ? <Form /> : null}
```

Допускаются простые условные `className`.

Допускается использование map если поля объектов уже содержат рассчитанными данные для вставки в jsx и не требуют доплнительных расчетов

---

# 29. Строки интерфейса

Текстовые UI-строки объявляются в начале компонента.

Не следует писать пользовательский текст непосредственно в JSX.

Пример:

```ts
const strSave = "Save";
const strCancel = "Cancel";
```

---

# 30. Обработчики в JSX

Не использовать inline-функции:

```tsx
onClick={() => doSomething()}
```

Вместо этого обработчик готовится заранее:

```ts
const onClickHandler = () => {
  doSomething();
};
```

и затем:

```tsx
onClick={onClickHandler}
```

Это правило относится именно к JSX.

Анонимные функции в обычном TypeScript-коде, `map`, `filter`, `useEffect` и подобных местах допустимы.

---

# 31. Форматирование TypeScript

Для коротких условий используется компактная запись:

```ts
if (selectionMode === "room") {
  return;
}
```

Не следует искусственно разбивать короткие условия:

```ts
if (
  selectionMode ===
  "room"
) {
```

Перенос нужен только тогда, когда выражение действительно длинное и не помещается нормально в строку.

Для функций:

- до 3 параметров — по возможности одна строка;
- 4 и более — допускается перенос.

# 35. Общий принцип

Бизнес-правила должны находиться в минимальном количестве мест.

Если решение зависит от:

- роли;
- статуса;
- режима интерфейса;
- вместимости;
- доступности;

то предпочтительно иметь одну функцию или один сервис, определяющий результат, вместо повторения одинаковых условий в нескольких компонентах.

Главная цель архитектуры — сохранить UI простым, бизнес-логику централизованной, а работу с базой данных изолированной от компонентов.
