# Архитектура проекта

## Слои приложения

Работа с данными разделена на слои:

```text
React component
    ↓
Entity service
    ↓
Database adapter
    ↓
Supabase / MariaDB API
```

Компоненты отвечают за интерфейс и вызывают сервисы сущностей. Компоненты не
должны выполнять прямые запросы к Supabase.

Сервисы содержат прикладную и бизнес-логику: подготовку данных для отображения,
сортировку, вычисление доступности, правила переходов статусов и операции над
сущностями. Сервисы работают с базой только через объект `db`.

`src/services/database.ts` — Supabase-реализация низкоуровневого Database Adapter.
`src/services/mariaDatabase.ts` предоставляет тот же клиентский контракт для MariaDB,
а SQL к MariaDB выполняется только серверным слоем `src/server/`. Компоненты и
entity services не должны выполнять прямые запросы ни к Supabase, ни к MariaDB.
Адаптер экспортирует API для сущностей:

```ts
db.users
db.roles
db.houses
db.rooms
db.houseMaps
db.retreats
db.retreatRooms
db.guests
db.guestStatuses
db.taxiRides
db.taxiGuests
```

В зависимости от сущности используются методы вроде `getAll()`, `getById()`,
`getByRetreatId()`, `create()`, `update()` и `delete()`. Для атомарных операций
гостя дополнительно используется `db.guests.swapRooms()`, а `create()` и `update()`
могут получить уже подготовленную сервисом запись статуса и записать обе сущности
в одной транзакции.

Database Adapter не содержит бизнес-вычислений и не принимает решения о доступности,
вместимости, статусе или отображаемом названии комнаты. Эти значения и проверки
готовятся в сервисах. Исключение — технический `id` нового гостя, который появляется
только после INSERT и подставляется адаптером в связанную status-запись.

## Структура исходного кода

Фактическая структура на данный момент:

```text
src/
├── app/                 # маршруты Next.js и глобальные стили
├── components/          # React-компоненты, сгруппированные по областям
│   ├── common/
│   ├── guests/
│   ├── history/
│   ├── houseMaps/
│   ├── houses/
│   ├── layout/
│   ├── retreats/
│   ├── rooms/
│   └── taxis/
├── contexts/            # React Context, включая текущего пользователя
└── services/            # бизнес-логика, Supabase-клиент и адаптер БД
```

В `src/services/` находятся адаптер `database.ts`, Supabase-клиент
`supabase.ts` и сервисы сущностей, например `guestsService.ts`,
`guestStatusesService.ts`, `houseMapsService.ts` и `taxiRidesService.ts`.

При добавлении функциональности располагайте код рядом с соответствующей
областью проекта и следуйте уже существующим соглашениям. Не создавайте новую
архитектурную структуру параллельно существующей без отдельной необходимости.

### Комментарии в сервисах

Перед нестандартными service-функциями оставляйте короткий комментарий на русском,
если функция реализует правило предметной области, неочевидную фильтрацию/сортировку,
агрегацию данных или подготовку атомарной операции. Очевидные CRUD-методы вроде
`get`, `create`, `update` и `delete` комментировать только ради самого комментария не нужно.

### Стиль TypeScript и JSX

- У arrow function с одним простым параметром скобки не ставятся: `item => ...`.
  Скобки остаются только там, где их требует синтаксис TypeScript, например для типизированного
  параметра или destructuring.
- Для условного JSX без альтернативной ветки используйте `condition && <Component />` вместо
  `condition ? <Component /> : null`. Если условие само не boolean и потенциально может вернуть
  отображаемое falsey-значение вроде `0`, сначала приводите его к boolean.
- Брендовое имя не используется в технических идентификаторах: CSS-классах, storage/cookie keys,
  package name, переменных, функциях, типах и внутренних id. Для технических префиксов используйте
  `project` или `proj`. Брендовое имя допустимо только как отображаемая эмблема.
- Function component всегда принимает один объект `props`; props не деструктурируются в параметрах
  функции. Внутри компонента используйте `props.propName`.
- Результат `useRetreat()` сохраняется целиком в `retreatContext`; не деструктурируйте его.
  Методы и поля контекста вызывайте как `retreatContext.methodName` / `retreatContext.snapshot`.
- Правила действий с гостем не дублируются в компонентах. Переходы статусов принадлежат
  `guestStatusesService`, а проверки операций с guest records/room swap — `guestsService`.
  Компонент отвечает только за UI-реакцию на уже определённое действие.

## Текущий пользователь

Текущий пользователь приложения доступен через React Context:

```ts
const { currentUser } = useCurrentUser();
```

Если service-операция создаёт audit/status запись, `currentUser.id` передаётся в
service явно как автор изменения. Service не должен сам искать пользователя с
фиксированным login вроде `admin`.

Если удобно, значение можно переименовать:

```ts
const { currentUser: user } = useCurrentUser();

if (!user) {
  return null;
}
```

Доступные поля пользователя:

```text
id
name
login
role
retreat_id
```

При смене пользователя интерфейс, использующий контекст, обновляется.

## Загрузка данных и границы ответственности

- Компоненты вызывают сервисы и не знают детали запросов к базе.
- Сервисы используют только Database Adapter для операций с базой.
- Бизнес-правила не должны дублироваться в нескольких компонентах.
- Данные для отображения следует подготовить до JSX `return`.
- Не загружайте данные в корневой компонент только ради передачи через длинную
  цепочку props, если их может загрузить соответствующая рабочая область.

### Снимок данных ретрита

Внутри `RetreatWorkspace` выбранный ретрит и его связанные данные предоставляет
`RetreatProvider` из `src/contexts/RetreatContext.tsx`. Компоненты рабочих
разделов используют `useRetreat()` вместо самостоятельной загрузки гостей,
статусов, поездок, комнат ретрита и домов. Общая загрузка агрегата находится в
`src/services/retreatSnapshotService.ts` и составляется из сервисов сущностей;
прямые запросы к Supabase из контекста и компонентов запрещены.

Контекст возвращает `snapshot`, выбранный `retreat`, состояние загрузки и
ошибку, методы чтения данных из снимка без повторного запроса, например
`getGuests()` и `getTaxiRides()`, lookup-функции `findGuest()`, `findRoom()`,
`findHouse()`, `findRetreatRoom()` и другие, а также `changeRetreat(retreatId)`,
`refresh()` и команды изменения данных. Retreat-scoped компоненты не должны
повторять `snapshot`-поиски вида `rooms.find(...)` или `retreatRooms.find(...)`,
если для этого lookup уже есть функция контекста.
Команды записывают изменения через существующие сервисы, затем перечитывают
снимок и публикуют его только если содержимое изменилось. Не выполняйте для тех
же сущностей дополнительные запросы в компонентах, если данные уже есть в
снимке.

`houses` и `rooms` считаются справочными данными: их сервисы загружают полный
список один раз и возвращают cache при последующих snapshot refresh. После
`create`, `update` или `delete` соответствующий сервис перечитывает таблицу,
поэтому следующий snapshot получает актуальный справочник без интервального DB IO.

Проверка запускается каждые пять секунд только пока вкладка видима. В скрытой
вкладке опрос прекращается; при возвращении к ней выполняется проверка сразу.
Пока у `retreats` нет поля `version`, контекст загружает агрегат целиком и
сравнивает содержимое со снимком. Если поле `version` доступно, проверки
сверяются по версии, а полная загрузка снимка всё равно выполняется не реже
одного раза в 120 секунд. Само добавление поля в TypeScript не создаёт столбец
в базе; для корректной инвалидации при изменениях связанных таблиц база должна
увеличивать версию ретрита при изменениях этих данных.

## Окружение Supabase

Локальные переменные хранятся в `.env.local`:

```env
NEXT_PUBLIC_SUPABASE_URL=https://<project-ref>.supabase.co
NEXT_PUBLIC_SUPABASE_ANON_KEY=<publishable-or-anon-key>
```

После изменения `.env.local` перезапустите `npm run dev`. Не размещайте
`service_role` или другой секретный ключ в переменной с префиксом
`NEXT_PUBLIC_`.

- Retreat-scoped компоненты получают отображаемое имя комнаты по `roomId` через `RetreatContext`; поиск `room + house` ради presentation string внутри компонента не допускается.
