# Атомарные записи гостей

## Граница ответственности

Бизнес-логика остаётся в entity services. Database Adapter только читает и
записывает данные и не должен:

- вычислять отображаемое название комнаты;
- решать, какой status создавать;
- проверять роль пользователя;
- вычислять доступность или вместимость комнаты;
- принимать решение, разрешён ли обмен комнатами.

Сервис выполняет проверки и передаёт адаптеру все значения в готовом виде.
Если операция создаёт status history, вызывающий слой передаёт service id текущего
пользователя, а service записывает его в `updated_by`; service не выбирает автора
из таблицы `users` по фиксированному login. Единственное техническое исключение —
`guest_id` нового гостя: при совместном создании гостя и status он неизвестен до
INSERT и подставляется адаптером после получения generated id.

## `db.guests.create()`

Без status выполняется обычный INSERT гостя. Если сервис передал status, адаптер
атомарно выполняет:

```text
INSERT guest
получить generated guest.id
INSERT guest_statuses с этим guest_id
COMMIT
```

## `db.guests.update()`

Без status выполняется обычный UPDATE. Если сервис определил смену комнаты и
передал полностью подготовленный status, UPDATE гостя и INSERT истории выполняются
в одной транзакции.

## `db.guests.swapRooms()`

Все места приложения должны выполнять обмен через `guestsService.swapRooms()`.
Сервис загружает гостей и их latest statuses, выполняет проверки (включая запрет обмена
для `not_coming`), рассчитывает новые `room_id`, подготавливает две status-записи и
вызывает один метод адаптера. Адаптер атомарно выполняет два UPDATE и два INSERT.

## Реализация backend'ов

Supabase использует PostgreSQL RPC-функции из
`supabase/migrations/202610070002_guest_write_transactions.sql`. Они содержат
только запись переданных значений. MariaDB использует один server-side connection
с `beginTransaction()`, `commit()` и `rollback()`.

## Конкурентные изменения

Проверки доступности и вместимости выполняются сервисами до записи. Это сохраняет
чистую границу Database Adapter, но не даёт строгой DB-level гарантии против двух
одновременных клиентов, которые оба прошли проверку последнего свободного места
до начала записи. Если такая гарантия станет обязательной, потребуется отдельный
механизм сериализации/блокировки либо ограничение на уровне backend-а.
